# dev-notes

> 실제 경험과 근거, 반복적인 개선을 통해 쌓아가는 내 개발 원칙들

**Working principles, not final answers.**

AI와 함께 소프트웨어를 개발할 때 사용하는 개인적인 판단 기준을 기록합니다. 특정 도구나 아키텍처를 정답으로 정하지 않고, 실제 개발 경험에 따라 원칙을 수정합니다.

## 개발 원칙

1. **요구사항 중심:** 기술 선택의 출발점은 실제 문제와 제약조건입니다. 좋은 설계는 요구사항을 정확하게 충족해야 합니다.
2. **근거 있는 선택:** AI의 추천을 참고하되 맹신하지 않습니다. 현재 문제와의 적합성, 널리 쓰이는 관행, 기존 경험과 시간 제약을 함께 고려합니다. 최적해를 확신하기보다 충분히 합리적인 선택을 합니다.
3. **설계는 함께, 구현은 위임:** AI가 우선 추천안과 이유를 제시하고 중요한 부분을 논의합니다. 구현은 AI에 위임하되, 시스템 구조·데이터 흐름·핵심 설계의 대안과 트레이드오프는 이해할 수 있어야 합니다.
4. **영향에 맞춘 검증:** 변경의 사이드이펙트와 데이터·보안 등 중요한 영향을 고려합니다. 검증 깊이는 요구사항, 영향도, 불확실성에 따라 조절합니다.
5. **함께 이해할 수 있는 변경:** 코드의 목적과 변경 이유를 다른 개발자도 파악할 수 있도록 합니다. 커밋과 PR은 줄 수보다 논리적 범위와 리뷰 가능성을 중요하게 생각합니다.
6. **전체 개발 비용 고려:** 구현 속도뿐 아니라 이해, 검증, 리뷰, 수정에 드는 시간까지 고려합니다. 과도한 추상화나 절차를 기본값으로 두지 않습니다.
7. **새로운 근거에 따라 개선:** 기존 선택이 틀렸을 수 있음을 인정합니다. 재설계 여부는 기대효과와 변경 비용을 비교해 판단합니다.

## AI와 협업하는 방식

- 새로운 프로젝트에서는 요구사항에 맞는 익숙하고 널리 쓰이는 구성을 출발점으로 삼되, 필요하면 다른 방식을 선택합니다. 기존 팀의 관례가 있다면 우선 이해하고 존중합니다.
- AI는 중요한 설계에 대해 **추천안 하나와 근거**를 먼저 제시합니다. 의미 있는 의문이나 추가 증거가 생기면 대안을 논의합니다. 모든 사소한 선택에 승인을 요구하지 않습니다.
- 큰 기능을 완성하면 **무엇을 만들었는지, 구조와 동작, 중요한 선택 이유, 검증 결과**를 쉬운 한국어로 간결하게 설명합니다. 모든 코드 줄을 설명할 필요는 없습니다.
- Issue, 커밋, PR, 결정 기록은 작업의 목적과 변경을 추적하는 데 유용할 때 사용합니다. 팀이 정한 협업 절차가 있다면 그 방식을 따릅니다.
- Claude Code와 Codex의 기본 기능을 신뢰합니다. 자체 하네스를 과도하게 만들거나 기존 기능을 불필요하게 제한하지 않습니다.

## 사용 방식

이 저장소의 지침은 다른 프로젝트에 자동 적용되지 않습니다. 각 프로젝트의 명시적인 요구사항과 팀 규칙이 우선이며, 필요한 원칙만 해당 프로젝트에 가져가 사용합니다.

사람이 읽고 판단하는 문서와 설명은 **쉽고 간결한 한국어**, 코드와 에이전트 전용 지침은 영어를 기본으로 합니다. 규칙이 실제 작업을 방해한다면 그 규칙도 고칩니다.
